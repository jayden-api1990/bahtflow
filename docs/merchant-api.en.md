# BahtFlow Pay Merchant API

Merchant integration guide. Base path is `/api/v1`. Amounts are in Thai Baht (THB).

Merchants should only call the APIs in this document. After a deposit is created successfully, give the returned `uploadUrl` to the player so they can open it and upload the transfer slip.

## Base URL

| Environment | Base URL |
|---|---|
| UAT | `https://bfpay-api.sbx888.net/api/v1` |
| PROD | `https://api.bahtflow.com/api/v1` |

The production URL is provided separately by BahtFlow Pay. Paths below are relative to this base path.

## Common rules

### Authentication

Every request is `POST` with `Content-Type: application/json`, and must include:

| Field | Location | Description |
|---|---|---|
| `merchant_serial` | body | Merchant ID assigned by BahtFlow Pay |
| `sign` | body | Request signature |

The merchant must be enabled. A disabled merchant returns 403, the same as an invalid `merchant_serial`.

### Signature (`sign`)

1. Take all request parameters except `sign`.
2. Sort by parameter name ascending (`ksort`).
3. Skip parameters whose value is `null` or an empty string `""`.
4. Convert arrays to JSON (`JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES`, with keys sorted).
5. Cast remaining values to strings.
6. Build a query string with `http_build_query(..., '', '&', PHP_QUERY_RFC3986)`.
7. Append the merchant `md5key` at the end with no separator.
8. `sign = md5(result)`, lowercase hex.

**Example**

Parameters:

```json
{
  "merchant_serial": "M001",
  "merchantOrderNo": "D20260930001",
  "amount": 100,
  "fromAccount": "0987654321",
  "fromBankCode": "004",
  "fullName": "Tester"
}
```

If `md5key` is `abc123`, the string to sign is:

```text
amount=100&fromAccount=0987654321&fromBankCode=004&fullName=Tester&merchantOrderNo=D20260930001&merchant_serial=M001abc123
```

`sign` is `32a9925a8f2d48bbbd2d0f2cd66187a8`.

Fields that contain spaces or non-ASCII characters are encoded per RFC 3986 before signing. Values sent in the request must match the values used for the signature.

### IP whitelist

If the merchant has at least one enabled IP configured, the request source IP must match one of them. If no IPs are configured, there is no source restriction.

When the IP is not whitelisted, HTTP 403 is returned:

```json
{
  "respCode": "9999",
  "respMsg": "IP address not whitelisted."
}
```

### Response format

**Success** (HTTP 200)

```json
{
  "respCode": "0000",
  "respMsg": "success",
  "data": {}
}
```

**Failure**

```json
{
  "respCode": "0002",
  "respMsg": "merchantOrderNo already exists."
}
```

| HTTP | Meaning |
|---|---|
| 200 | Business success; check `respCode=0000` |
| 400 | Business failure, `respCode=9999` |
| 403 | Merchant, signature, or IP check failed, `respCode=9999` |
| 422 | Validation failed, or duplicate merchant order number, `respCode=0002` |

When creation is rejected, HTTP 400 is returned; `data.upstreamCode` is the error code and `data.upstreamData` is additional data.

| respCode | Description |
|---|---|
| `0000` | Success |
| `0002` | Invalid parameters, or `merchantOrderNo` already exists |
| `9999` | Signature/IP/merchant error, insufficient credit, order not found, order already final, missing callback URL, or creation rejected |

### Merchant order number

`merchantOrderNo` is generated by the merchant and must be unique per merchant (shared across deposits and withdrawals). Maximum length is 64 characters.

### Callback URL

A per-request `callbackUrl` may be provided. If omitted, the callback URL from the merchant profile in the admin console is used. If both are empty, creating a deposit or withdrawal will fail.

After an order reaches a status that requires notification, BahtFlow Pay `POST`s JSON to that URL. Callbacks use the same signature algorithm, with `sign` in the body.

### Bank codes

## 1. Create deposit

Create a deposit and match it automatically. On success, give `uploadUrl` to the player. The player transfers the exact amount to the accounts in `matchedWithdraws`, then opens the link and uploads the slip before expiry.

This API does not change merchant credit. Credit is increased when the deposit callback status is `complete`.

| | |
|---|---|
| Method | `POST` |
| Path | `/deposit` |

### Request body

| Field | Type | Required | Description |
|---|---|---|---|
| `merchant_serial` | string | Yes | Merchant ID |
| `sign` | string | Yes | Signature |
| `merchantOrderNo` | string | Yes | Merchant order number, max 64 |
| `amount` | number | Yes | Amount, greater than 0 |
| `fromAccount` | string | Yes | Player payer account number |
| `fromBankCode` | string | Yes | Payer bank code |
| `fullName` | string | Yes | Payer account name |
| `fullNameEn` | string | No | Payer account name in English |
| `callbackUrl` | string | No | Callback URL for this order; must be a URL |
| `returnUrl` | string | No | Redirect URL after the slip page finishes |

### Success `data`

| Field | Description |
|---|---|
| `merchantOrderNo` | Merchant order number |
| `ref` | Platform order number; used in later callbacks |
| `amount` | Amount as a string |
| `status` | `pending` |
| `expiredDate` | Expiry time |
| `uploadUrl` | Page where the player uploads the slip |
| `uploadToken` | Token for the upload page |
| `matchedWithdraws` | Target accounts the player should transfer to |

Each item in `matchedWithdraws` includes `ref`, `amount`, `toAccount`, `toBankCode`, `toAccountName`, and bank name fields.

```json
{
  "respCode": "0000",
  "respMsg": "success",
  "data": {
    "merchantOrderNo": "D20260930001",
    "ref": "JINLP-D-20260402-120100-YYYYYY",
    "amount": "100",
    "status": "pending",
    "expiredDate": "2026-04-02T12:16:00.000Z",
    "uploadUrl": "https://slip.example/JINLP-D-20260402-120100-YYYYYY?t=TOKEN",
    "uploadToken": "TOKEN",
    "matchedWithdraws": [
      {
        "ref": "JINLP-W-20260402-120000-XXXXXX",
        "amount": 100,
        "toAccount": "1234567890",
        "toBankCode": "004",
        "toAccountName": "ACCOUNT NAME"
      }
    ]
  }
}
```

## 2. Cancel deposit

Cancel a deposit that has not yet reached a final status. Prefer an explicit cancel over waiting for timeout.

| | |
|---|---|
| Method | `POST` |
| Path | `/deposit/cancel` |

### Request body

| Field | Type | Required | Description |
|---|---|---|---|
| `merchant_serial` | string | Yes | Merchant ID |
| `sign` | string | Yes | Signature |
| `merchantOrderNo` | string | Yes | Merchant order number used when creating the deposit |

### Success `data`

```json
{
  "respCode": "0000",
  "respMsg": "success",
  "data": {
    "merchantOrderNo": "D20260930001",
    "ref": "JINLP-D-20260402-120100-YYYYYY",
    "status": "cancelled"
  }
}
```

If the order does not exist, the response is `Order not found.`. If the order is already final, the response is `Order is already final.`. Cancel does not decrease or increase credit.

## 3. Create withdrawal

On successful creation, the full amount is locked immediately and credit decreases. If creation is rejected, credit is not locked, no order is created, the API returns an error directly, and no callback is sent.

| | |
|---|---|
| Method | `POST` |
| Path | `/withdraw` |

### Request body

| Field | Type | Required | Description |
|---|---|---|---|
| `merchant_serial` | string | Yes | Merchant ID |
| `sign` | string | Yes | Signature |
| `merchantOrderNo` | string | Yes | Merchant order number, max 64 |
| `amount` | number | Yes | Amount, greater than 0, and not exceeding current credit |
| `toAccount` | string | Yes | Payee account number |
| `toBankCode` | string | Yes | Payee bank code |
| `toAccountName` | string | Yes | Payee account name |
| `toAccountNameEn` | string | No | Payee account name in English |
| `callbackUrl` | string | No | Callback URL for this order; must be a URL |

### Success `data`

```json
{
  "respCode": "0000",
  "respMsg": "success",
  "data": {
    "merchantOrderNo": "W20260930001",
    "ref": "JINLP-W-20260402-120000-XXXXXX",
    "amount": "100",
    "status": "pending",
    "expiredDate": "2026-04-02T12:30:00.000Z"
  }
}
```

When credit is insufficient, HTTP 400:

```json
{
  "respCode": "9999",
  "respMsg": "Insufficient merchant credit."
}
```

## 5. Merchant callbacks

BahtFlow Pay sends a `POST` to this order’s `callbackUrl` (or the merchant’s default callback URL) with `Content-Type: application/json`.

Return HTTP 2xx. BahtFlow Pay currently delivers once; a timeout of 8 seconds or a non-2xx response is recorded as a failed notification and is not retried automatically.

Use `ref` + `status` for idempotency. Do not move a final status back to an intermediate status.

### Callback body

| Field | Description |
|---|---|
| `type` | `deposit` or `withdraw` |
| `merchantOrderNo` | Merchant order number |
| `ref` | Platform order number |
| `status` | See tables below |
| `amount` | Order amount |
| `completedAmount` | Completed amount |
| `remainingAmount` | Remaining amount |
| `sign` | Computed with the same signature algorithm using the merchant’s `md5key` |

```json
{
  "type": "deposit",
  "merchantOrderNo": "D20260930001",
  "ref": "JINLP-D-20260402-120100-YYYYYY",
  "status": "complete",
  "amount": "100",
  "completedAmount": "100",
  "remainingAmount": "0",
  "sign": "..."
}
```

### Deposit statuses

| status | When notified | Credit |
|---|---|---|
| `complete` | Deposit completed | Increased once by the order amount |
| `cancelled` | Cancelled by merchant, or order cancelled | Unchanged |
| `cancelled_by_admin` | Force-cancelled by admin | Unchanged |
| `timeout` | Timed out | Unchanged |

If deposit creation is rejected, the API returns an error synchronously and no callback is sent.

### Withdrawal statuses

The full amount is deducted on successful creation. The final callback only refunds the incomplete portion: `refund amount = locked amount - completedAmount`.

| status | When notified | Credit |
|---|---|---|
| `update` | Intermediate progress. Reports current `completedAmount` and `remainingAmount` | Unchanged |
| `complete` | Fully completed | No refund |
| `complete_below_min` | Auto-completed after remaining amount fell below the minimum | Incomplete portion refunded |
| `timeout` | Timed out | Incomplete portion refunded |
| `cancelled` | Cancelled | Incomplete portion refunded |
| `cancelled_by_admin` | Force-cancelled by admin | Incomplete portion refunded |
| `failed` | Order failed | Incomplete portion refunded |

Both `update` and final statuses for withdrawals notify the merchant. Each callback reflects the current progress; overwrite local records with the latest `completedAmount` and `remainingAmount` — do not sum amounts across multiple `update` callbacks. After an order is final, later callbacks are ignored. Credit is settled only on final statuses.

### Credit example

Withdrawal of 100, merchant credit was 500:

1. Creation succeeds; credit becomes 400.
2. Final `completedAmount=40`, `remainingAmount=60`; 60 is refunded; credit becomes 460.
